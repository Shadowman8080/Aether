test checklist

Printable field checklist for disposable x86_64 hardware

One copy per machine · Plan: secure-boot-physical-test-plan.md · Evidence template: secure-boot-evidence-template.json

Destructive test. This procedure clears firmware Secure Boot keys, erases the test disk and changes the firmware forbidden-signature database. Use only a machine that can be erased and recovered. Do not use production disks, production keys or a machine whose vendor keys cannot be restored.

Read the full plan before starting. This checklist is the field record; the plan contains the detailed rationale, commands and limitations. A test that was not run is not a pass.

Before you touch firmware

Stop now if any answer is no. A disposable machine, a tested vendor-key recovery path and backups are prerequisites, not optional preparation.
  • ☐ I confirm this is a disposable test machine, not a production or daily-use system.
  • ☐ I have backed up all data and recorded the vendor, model, serial and firmware version.
  • ☐ BitLocker, LUKS, TPM-bound unlocking and similar protection are disabled; recovery keys are available outside the test media.
  • ☐ Every disk that is not the disposable test target is removed or disconnected.
  • ☐ I know how to restore the vendor Secure Boot keys by firmware menu, factory restore or reflash.
  • ☐ CSM/legacy boot and Fast Boot are disabled; UEFI boot is selected.
  • ☐ The exact release ISO hash matches the expected value below.
  • ☐ The ISO was written to the whole USB device with dd conv=fsync, not to a partition.
  • ☐ A second FAT32 USB is prepared with an unsigned EFI test binary at EFI/BOOT/BOOTX64.EFI.
  • ☐ Public db.crt, db.der, PK.auth, KEK.auth and db.auth are available on a trusted host.
  • ☐ No release private key or build-host private key is on the test machine or test media.
  • ☐ A camera or serial console is ready for photographs and exact firmware messages.
  • ☐ The evidence directory exists and is writable.

1. Firmware baseline and negative controls

FW-01 required — Firmware baseline and Setup Mode

  • ☐ Enter firmware setup. Disable CSM/legacy support, enable UEFI, and disable Fast Boot.
  • ☐ Record the initial Secure Boot state, Secure Boot mode, PK/KEK/db ownership and whether vendor keys are present.
  • ☐ Photograph the firmware identity, Secure Boot and key-management screens.
  • ☐ Confirm the vendor-key restore/factory-reset/reflash path is available.
  • ☐ Do not clear the keys yet. Complete FW-02 and LIVE-02 below while the vendor keys are still present.

Expected baseline: Initial state is recorded; the vendor-key recovery path is documented; vendor keys are still present. Complete the Setup Mode transition after the two controls below.

FW-02 required — Unsigned EFI binary rejected

  • ☐ On the trusted host, verify the test binary is unsigned or not signed by a trusted key. A rejected sbverify is expected.
  • ☐ Place it at EFI/BOOT/BOOTX64.EFI on the second FAT32 USB.

3. Signed live media

LIVE-01 required — Signed live ISO with Secure Boot on

  • ☐ Boot the same verified USB in UEFI mode with Secure Boot enabled.
  • ☐ Confirm the Aether live session reaches the graphical live desktop.
  • ☐ Record AETHER_LIVE_AUTOLOGIN and AETHER_LIGHTDM_START if a serial console is available; otherwise photograph the desktop.
  • ☐ Run the status command and save live-journal.txt from the journal/dmesg checks.
pkexec /usr/libexec/aether-secureboot-enroll --status
sudo journalctl -b -k | grep -iE 'secure boot|lockdown|efi'
sudo dmesg | grep -iE 'secure boot|lockdown'

Expected: secure_boot=true, setup_mode=false, aether_key_enrolled=true, can_enroll=false; no firmware violation; live desktop is reached.

  • ☐ Optional negative control: a second USB with the Aether db removed or a deliberately invalid signed UKI is rejected by firmware. Do not modify the only release USB.
Live desktop reached: ☐ Yes   ☐ No   Firmware violation: ☐ None   ☐ Seen

4. Install the signed chain

INSTALL-01 required — Signed install

  • ☐ From the signed live session, open the installer.
  • ☐ Select the disposable target disk only.
  • ☐ Confirm the installer reports Secure Boot is enabled and Aether's signed boot chain is enrolled or the equivalent enabled status.
  • ☐ For this required baseline, leave LUKS/encryption off; encrypted/LVM boot is lab-tested under OVMF and is not part of this physical pass count.
  • ☐ Confirm erase, install, and wait for completion. Record the completion message and any errors.
  • ☐ Shut down, remove the USB, and boot the installed disk in UEFI mode with Secure Boot still enabled.

Expected: The installer reports an enabled enrolled chain and the install completes without errors.

5. Verified installed boot

INSTALL-02 required — Installed boot and signature verification

  • ☐ Sign in at aether login:. Complete the first-boot password change if prompted and reach Plasma.
  • ☐ Record firmware state and the Aether boot entry.
  • ☐ Inspect the ESP and save esp-files.txt with ownership, sizes and SHA-256 hashes.
  • ☐ Verify all three signatures with sbverify from a trusted host or the live media; save sbverify.txt and the tool version.
pkexec /usr/libexec/aether-secureboot-enroll --status
efibootmgr -v
sudo findmnt /boot/efi
sudo ls -l /boot/efi/EFI/BOOT /boot/efi/EFI/aether
sudo sha256sum /boot/efi/EFI/BOOT/BOOTX64.EFI \
  /boot/efi/EFI/BOOT/grubx64.efi /boot/efi/EFI/aether/aether.efi
sudo mount -o ro /dev/sdXN /mnt/esp
sbverify --cert db.crt /mnt/esp/EFI/BOOT/BOOTX64.EFI
sbverify --cert db.crt /mnt/esp/EFI/BOOT/grubx64.efi
sbverify --cert db.crt /mnt/esp/EFI/aether/aether.efi
sbverify --version

Expected: secure_boot=true, aether_key_enrolled=true; the boot entry points to the signed ESP loader; all three sbverify checks pass.

6. Revocation and recovery

Destructive. Complete the install and recovery steps first. Keep the vendor firmware recovery path available. Revocation tests exercise firmware and a laboratory hierarchy; they are not a shipped Aether revocation feature.

REVOKE-01 required — Add Aether db certificate to firmware dbx

  • ☐ On the trusted host, convert the public certificate to DER.
  • ☐ Put it on a FAT32 USB. In firmware key management, append it to dbx / Forbidden Signature Database.
  • ☐ Record whether firmware accepted a certificate, hash or ESL, and photograph the screen.
  • ☐ Reboot with Secure Boot enabled and try both the Aether live USB and installed disk.
  • ☐ Both must be rejected by firmware before shim or GRUB runs. Photograph the exact messages and save the firmware log.
  • ☐ If either still boots, FAIL: stop and preserve logs. Do not continue to other revocation variants.
openssl x509 -in db.crt -outform DER -out aether-db.der

Expected: Firmware accepts the entry and rejects both media before the Aether chain starts. Firmware without a dbx UI is BLOCKED, not pass.

Entry type accepted: ☐ Certificate   ☐ Hash   ☐ ESL   ☐ No dbx support
Live rejected: ☐ Yes   ☐ No   Installed rejected: ☐ Yes   ☐ No
Result: ☐ PASS   ☐ FAIL   ☐ BLOCKED   ☐ NOT RUN   Evidence: revocation-dbx.jpg, revocation-boot-failure.jpg

REVOKE-02 supplemental — Unsigned dbx update refused

This checks firmware update enforcement. It is not a requirement for the physical Aether pass; record it when the firmware supports the operation.

  • ☐ Save the current dbx contents before the attempt.
  • ☐ Try an unsigned or wrongly signed dbx update with efi-updatevar.
  • ☐ Confirm the update is refused and the dbx contents are unchanged.
sudo efi-readvar -v dbx > dbx-before.txt
sudo efi-updatevar -f unsigned.auth dbx
sudo efi-readvar -v dbx > dbx-after.txt

Expected: Refusal; before and after dbx state match. Mark BLOCKED if this operation is unavailable.

Result: ☐ PASS   ☐ FAIL   ☐ BLOCKED   ☐ NOT RUN   Evidence: dbx-unsigned-refused.txt

REVOKE-03 laboratory only — Signed dbx update

Use only a disposable test machine or VM and a disposable test PKI. Never use Aether release private keys. This is not a production rotation or revocation procedure.

  • ☐ Generate a disposable PK/KEK/db hierarchy and enroll it on the test machine/VM. Keep private keys off the test media.
  • ☐ Build a dbx ESL containing the test db certificate and sign it with the test KEK.
  • ☐ Apply the signed update; reboot and confirm the test image signed by that db is rejected.
  • ☐ Try an unsigned or wrong-KEK update; firmware must refuse it and leave dbx unchanged.
  • ☐ Rotation: enroll a new test db, sign a new test image, and confirm the old image is rejected while the new one boots.
cert-to-efi-sig-list test-db.crt test-db.esl
sign-efi-sig-list -k test-KEK.key -c test-KEK.crt dbx test-db.esl test-db.auth
sudo efi-updatevar -f test-db.auth dbx

Expected: Signed update works for the disposable test image; wrong-key update is refused; rotation follows the test hierarchy. Record as lab evidence only.

Result: ☐ PASS (lab)   ☐ FAIL   ☐ BLOCKED   ☐ NOT RUN   Evidence: dbx-signed-lab.txt

SBAT-01 unsupported — SBAT revocation

Status: UNSUPPORTED for shipped Aether media. Do not mark this test pass because the shim boots, and do not apply an unsigned SBAT update.

  • ☐ Record the installed shim SBAT metadata if a tool is available.
  • ☐ Record the OVMF lab-fixture result separately, if it was run; it does not make SBAT a physical pass.
  • ☐ Do not apply an unsigned SBAT update to this machine.
objcopy --dump-section .sbat=shim.sbat shimx64.efi
strings shim.sbat

A physical SBAT pass would require a separately reviewed, signed update for the Aether chain and a recovery procedure. None exists in this build.

Status: UNSUPPORTED   Evidence: sbat-metadata.txt

REVOKE-04 required — Recovery and re-enrollment

  • ☐ Enter firmware setup. Delete the dbx entry if possible, or clear all Secure Boot keys. Record exactly what was done.
  • ☐ Verify dbx no longer contains Aether's certificate. If clearing did not remove it, use factory-key restore or reflash.
  • ☐ If the intended end state is vendor-managed without Aether, restore vendor keys and stop.
  • ☐ For Aether recovery, leave Setup Mode active. Boot the Aether ISO with Secure Boot off and enroll the public PK.auth, KEK.auth and db.auth.
  • ☐ Enable Secure Boot, then confirm the signed live ISO and the installed disk both boot again.

Expected: The revocation entry is gone; Setup Mode is reached; Aether enrollment succeeds; both signed live and installed media boot. Recovery proves the machine is usable, not production key rotation or custody.

Known limitations acknowledged

  • ☐ Results apply only to this machine, firmware version and ISO hash.
  • ☐ The Aether PK/KEK/db hierarchy is build-host material, not an HSM-backed release root.
  • ☐ Aether has no production revocation, SBAT-update or key-rotation tooling.
  • ☐ The installed signed UKI includes a generic initramfs with LUKS2/LVM support, but encrypted boot has only OVMF lab evidence; physical encrypted-root coverage remains open.
  • ☐ No TPM measured boot or attestation was tested.
  • ☐ SBAT-01 is unsupported for shipped media; the lab fixture is separate evidence.
